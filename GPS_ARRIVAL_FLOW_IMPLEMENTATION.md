# GPS arrival and passenger confirmation

Implemented September 6, 2026. Arrival uses the existing persisted convoy journey states in both normal and Testing Mode. The subsequent runtime-path audit and deployment limitations are documented in [GPS_ARRIVAL_VERIFICATION.md](GPS_ARRIVAL_VERIFICATION.md).

| Requested detail | Implementation |
| --- | --- |
| 1. Why “Arrived at Pickup — TEST” appeared | `_currentPrimaryAction` explicitly returned direct arrival actions when `_bypassTransactionValidation` was enabled. GPS automation already existed alongside those actions. Removed all three manual arrival branches and their handlers. |
| 2. Files changed for this request | `lib/screens/driver/driver_package_tracking_screen.dart`, `lib/core/services/stable_arrival_detector.dart`, `lib/core/supabase/touristrike_repository.dart`, `supabase/migrations/20260906030000_keep_debug_arrivals_gps_verified.sql`, `supabase/tests/event_driven_trip_regression.mjs`, `test/gps_arrival_quality_test.dart`, `test/test_mode_convoy_markers_test.dart`, `test/developer_settings_test.dart`, `test/live_transaction_audit_test.dart`, and this report. Earlier uncommitted booking/payment/marker changes are preserved. |
| 3. Location service | Existing Geolocator position stream and periodic current-fix recovery; existing `upsertDriverLiveLocation` writes the authenticated driver's `driver_live_locations` row. Existing debug coordinates feed the same fix validation and arrival detector. |
| 4. Radius | The follow-up verification centralized the existing 150 m value in SQL `driver_arrival_radius_meters()`. The screen loads it into `_proximityMeters` before constructing the detector; SQL proximity and fallback checks call the same function. No hardcoded Flutter fallback. |
| 5. GPS noise and quality | Three distinct inside-radius fixes spanning at least six seconds. Outside-radius fixes, bad quality, or a gap over 20 seconds break the streak. Uploads require finite coordinates within geographic bounds, accuracy between 0 and 50 metres, age at most 20 seconds, and no timestamp more than two seconds ahead. Duplicate timestamps do not count twice. Future-dated bad samples cannot poison later samples. Older fixes cannot replace newer locally accepted ones. |
| 6. Idempotency | In-flight guard, retry throttle, and successful-arrival keys scoped to booking/state/stop prevent repeated local requests and banners. Only successful transitions reserve a key. Backend same-state no-ops retain timestamps and avoid repeat writes/logs/notifications; persisted state prevents replay after reopening. |
| 7. Actual arrival persistence | Existing transition updates the authenticated driver's `booking_drivers.journey_state` and `state_updated_at`; `trip_status_logs` retain transition history. Stop triggers insert `booking_driver_arrivals.arrived_at` once per assignment/item and set shared `booking_itinerary_items.actual_arrival_time`. Existing pickup milestone triggers populate booking/activity `arrived_at`. No new timestamp columns. |
| 8. Pickup | Start Navigation enters `en_route_pickup`. Passive heading/GPS text replaces the arrival button. GPS enters `at_pickup` and shows the pickup arrival banner. Tourist Picked Up remains manual, enters `boarded`, saves existing pickup milestones, and existing readiness handling starts the first leg once the convoy is ready. |
| 9. Stop arrival | Target comes from this driver's `current_stop_index`. Stable proximity enters `at_stop`, shows the destination name, persists arrival, and starts the stay display. |
| 10. Stay | This driver's persisted arrival `state_updated_at` anchors the configured stay. UI shows actual arrival, configured stay, expected departure, and remaining time. Planned itinerary arrival/departure values remain separate. |
| 11. Proceed | Existing `completeCurrentItineraryItem` records the driver's readiness after the stay (or authorized testing bypass). Existing readiness polling/realtime automatically starts the next leg once convoy gates clear. Existing departure triggers save `booking_driver_arrivals.departed_at` when movement actually begins. No second Navigate button. Final stop uses Finish Tour Stops; normal remaining-payment gating and Tourist payment modal remain in place before drop-off. |
| 12. Drop-off arrival | Stable GPS proximity enters `at_dropoff` and shows the drop-off banner. It does not confirm passenger alighting. |
| 13. Tourist Dropped Off | Existing completion action enters `completed`, persists assignment `completed_at` and drop-off milestone, and uses the existing convoy/payment finalizer. Location streaming is cancelled for this completed assignment; recovery/upload paths also check its completion independently of overall booking completion. |
| 14. Multi-driver | Each detector runs against its authenticated driver's position and assignment. Arrival RPC updates only that driver's row. Existing convoy readiness gates remain; one driver's GPS cannot mark another driver arrived or complete the convoy. |
| 15. Tourist realtime | Existing subscriptions to `booking_drivers`, `package_activities`, `booking_itinerary_items`, and `driver_live_locations` consume the server transitions and location updates. Existing server notification deduplication remains. No local-only replacement statuses. |
| 16. Testing Mode | Direct arrival buttons are removed in both modes. Repository always routes arrival targets to the canonical RPC even if the automatic-arrival hint is omitted. New SQL debug wrapper also keeps its bypass flag false for all three arrival targets, so direct debug RPC calls still require proximity. Operational schedule/payment/stay testing paths remain intact and never fabricate payment confirmation. |
| 17. Fallback | Retry GPS and Verify Arrival Manually appear for GPS/service/permission/sync failures or 30 seconds without a usable fix, in both modes. Time spent driving with healthy GPS no longer exposes the fallback. Existing fallback RPC requires a reason and recent driver or corroborating tourist proximity and writes an audit log. If GPS arrives while the dialog is open, or the target changes, the pending fallback is discarded. It cannot verify arrival without the server's corroborating location evidence. |
